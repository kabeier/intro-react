Why write tests at all?

  • Finding a bug by clicking around takes minutes; a test re-checks it in seconds, every time
  • A bug in production costs users, money and trust
  • Tests let you change code (unit 4 rewrites the whole page!) and know nothing broke

A test is a check you never have to do by hand again.

Say: "In unit 4 we rewrite this page in React state. These tests will tell us if we broke anything."

Three kinds of tests

KindAsksExampleTool
Unit"Does this function work?"calculateTax(100) returns 8Jest (fundamentals week)
Integration"Do these parts work together?"the form sends what the API expectsJest, Testing Library
End-to-end"Can the user actually use the feature?"search Bulbasaur → its card appearsCypress

Many small unit tests, fewer end-to-end tests: e2e tests are slower but closest to the user.

The testing pyramid: unit at the bottom (many, fast), e2e at the top (few, slow, most realistic).

Why Cypress

  • Runs your app in a real browser
  • Waits by itself: retries a check up to 4 s
  • Shows each step: you can see the test click and type
  • Can stub the network (lecture 2)
  • Tests read like the feature: visit, type, click, should…
  • Same describe / it words as Jest, but assertions are .should(…) chains

Cypress drives a browser like a user, and checks what the user would see.

Say: "Cypress commands are queued and run one after another; you don't use their return values like in Jest."

Anatomy of a test

PieceMeans
beforeEach(() => { … })runs before every test
it('should have a heading', () => { … })one test: a sentence about the app
cy.visit('/')open baseUrl + "/"
cy.get('header')find elements (CSS selector), waiting up to 4 s
.should('be.visible')what must be true (retried until it is)

Visit, find, check. Every test starts on a blank page.

Reading a red test

Cypress saysUsually means

Not enough / Too many elements foundthe count in have.length is off
The chainer `…` was not founda typo in the assertion name
cy.visit() failed trying to loadapp not running, or baseUrl wrong

The first line of the error tells you which of these it is.

Tests change when the app changes

  • starts with an empty poke container is true today
  • In unit 4, Pikachu loads when the page opens: that test will fail, on purpose
  • We will rewrite it to say what the app does then, and every other test stays

A failing test after a planned change = update the test. An unplanned one = a bug.

Say: "From unit 4 on, every feature starts with a failing test."
